## What this repo is

The **CipherTrust Terraform Provider** lets users manage Thales CipherTrust Manager (CM)
resources using Infrastructure-as-Code. It translates `terraform plan/apply/destroy` calls
into CipherTrust Manager REST API calls. It is published at
`github.com/ThalesGroup/terraform-provider-ciphertrust` on branch `1.0.1`.

CipherTrust Manager (CM) is Thales's enterprise key-management platform. Provider
sub-areas: **CM** (core platform), **CCKM** (cloud key-management — AWS/Azure/GCP/OCI),
**CTE** (CipherTrust Transparent Encryption — file/volume encryption policies).

## ⚠ Critical project constraint — TFIN-174

**Empty `Read()` is the root cause of ALL drift issues.** Every resource's `Read` method
currently returns without calling the CM API, so Terraform never reconciles state against
reality. This masks all other bugs (immutable-field violations, case mismatches, tag swaps).

**Fix order is mandatory:**
1. Fix `Read()` first (TFIN-174) — once API is called during plan, all drift becomes visible.
2. Fix `RequiresReplace` on immutable fields (TFIN-183, TFIN-179, TFIN-181).
3. Fix case normalization and JSON tag issues (TFIN-195, TFIN-194).

If your task is NOT TFIN-174, do not implement a proper `Read()` as a side-effect — it will
surface drift before the immutable-field fixes are in and will confuse users. Leave `Read()`
empty unless the ticket specifically asks you to fix it.

# Implementation Plan: TFIN-194 — Fix swapped JSON tags for revocation fields

## Root cause

In `internal/provider/cm/schema_cm.go`, the `CMKeyJSON` struct declares Go fields `RevocationReason string` and `RevocationMessage string`, but their `json:"..."` struct tags are transposed: `RevocationReason` is tagged `json:"revocation_message,omitempty"` and `RevocationMessage` is tagged `json:"revocation_reason,omitempty"`. Marshaling for Create/Update therefore sends each user-supplied value under the opposite JSON key, so CipherTrust Manager persists them in the wrong fields.

Because every resource's `Read()` is intentionally a no-op pending TFIN-174, this corruption is not currently surfaced as plan drift. The fix is strictly a serialization correction; no `Read()` work is in scope.

## Files to MODIFY

### 1. `internal/provider/cm/schema_cm.go` (the only code fix)

- In the `CMKeyJSON` struct, swap the `json` struct tags on the two fields so:
  - `RevocationReason` → `json:"revocation_reason,omitempty"`
  - `RevocationMessage` → `json:"revocation_message,omitempty"`
- Preserve the existing Go field names, types, and `,omitempty` modifiers. Do not rename Go identifiers — this keeps every existing call site in `resource_cm_key.go` correct without further edits.
- Audit the entire `internal/provider/cm/schema_cm.go` file for any other struct that carries these two tags (e.g., a dedicated revoke-request payload). Based on current inspection, `CMKeyJSON` is the only struct in this file containing `revocation_reason`/`revocation_message` tags; no secondary struct needs editing. If grep during implementation reveals an additional occurrence, apply the same tag swap there.

**Pattern to follow:** the JSON payload struct conventions in `internal/provider/cm/schema_cm.go` itself — every other field in `CMKeyJSON` (e.g., `Name`, `Algorithm`, `KeySize`) uses a snake_case `json` tag that exactly matches the CM API field name. Restore that convention for the two revocation fields. No cross-package "analogous" reference is needed.

### 2. `internal/provider/cm/resource_cm_key.go` (verification only — no code change)

- Verified current schema (in the `Schema()` method on the resource): `revocation_reason` is `schema.StringAttribute` with `Optional: true`; `revocation_message` is `schema.StringAttribute` with `Optional: true`. Neither is `Computed` or `Required`. No schema change is needed.
- Verified Go-side wiring: the `Create` and `Update` methods build a `CMKeyJSON` payload and assign `payload.RevocationReason = plan.RevocationReason.ValueString()` and `payload.RevocationMessage = plan.RevocationMessage.ValueString()`. The Go assignments are correct; only the JSON tags were wrong.
- Per TFIN-174, `Read()` remains an intentional no-op. Do not add read logic in this ticket.

## Schema changes

None. No new attributes, no type changes, no Required/Optional/Computed adjustments.

## Breaking-change considerations

- No `RequiresReplace` impact — revocation fields are mutable lifecycle attributes.
- No state migration — Terraform state already holds the user's intended values under the correct attribute names; only the wire format was wrong.
- User-visible effect: the next Update on a previously-revoked `ciphertrust_cm_key` will overwrite CM-side storage with the values now sent under the correct JSON keys. CM-stored reason/message may visibly swap on first apply. Call this out in the changelog.
