## What this repo is

The **CipherTrust Terraform Provider** lets users manage Thales CipherTrust Manager (CM)
resources using Infrastructure-as-Code. It translates `terraform plan/apply/destroy` calls
into CipherTrust Manager REST API calls. It is published at
`github.com/ThalesGroup/terraform-provider-ciphertrust` on branch `1.0.1`.

CipherTrust Manager (CM) is Thales's enterprise key-management platform. Provider
sub-areas: **CM** (core platform), **CCKM** (cloud key-management — AWS/Azure/GCP/OCI),
**CTE** (CipherTrust Transparent Encryption — file/volume encryption policies).

use `resource.Resource` / `datasource.DataSource` interfaces from
`github.com/hashicorp/terraform-plugin-framework`.

## ⚠ Critical project constraint — TFIN-174

**Empty `Read()` is the root cause of ALL drift issues.** Every resource's `Read` method
currently returns without calling the CM API, so Terraform never reconciles state against
reality. This masks all other bugs (immutable-field violations, case mismatches, tag swaps).

**Fix order is mandatory:**
1. Fix `Read()` first (TFIN-174) — once API is called during plan, all drift becomes visible.
2. Fix `RequiresReplace` on immutable fields (TFIN-183, TFIN-179, TFIN-181).
3. Fix case normalization and JSON tag issues (TFIN-195, TFIN-194).

If your task is NOT TFIN-174, do not implement a proper `Read()` as a side-effect — it will
surface drift before the immutable-field fixes are in and will confuse users. Leave `Read()`
empty unless the ticket specifically asks you to fix it.

- **Severity**: TBD – Requires clarification (severity not provided in ticket text; **must be pulled from Jira before merge** per critic point 9)
- **Impact**: Terraform users of five CM resources cannot detect out-of-band deletion or attribute drift. State is permanently frozen at create-time. No error or warning is surfaced. Affects `ciphertrust_cm_key`, `ciphertrust_cm_group`, `ciphertrust_cm_ssh_key`, `ciphertrust_cm_user_pwd_change`, `ciphertrust_cm_reg_token`.

### Root Cause
The `Read()` method on each of the five affected resources is implemented as either an empty function body or reads only from local prior state without calling the CM API. The Plugin Framework contract requires `Read()` to fetch live state and call `resp.State.Set()` (or `resp.State.RemoveResource()` on 404). With no API call, Terraform has no signal to detect deletion or drift, so plan/refresh reports "no changes" unconditionally.

### Why Existing Controls Failed
- No acceptance test asserted out-of-band-delete or drift behavior for these five resources, so the empty Reads passed CI.
- The CCKM subsystem and `ciphertrust_cm_user`/`ciphertrust_scheduler` established the correct pattern, but the five affected CM resources were not audited against it.
- TFIN-174's "intentionally empty Read" policy masked the defect — the empty Reads looked like project standard rather than a bug for these specific resources.
- Code review did not flag the empty bodies because adjacent resources also had empty Reads.

### Corrective Actions
- Implement real `Read()` for the affected resources (four definite + one conditional) following the verified ticket-named reference pattern.
- Reuse the verified shared 404-detection helper for consistent removal-on-delete behavior.
- Preserve write-only/sensitive attributes from prior state; assert this with positive test coverage.
- For `ciphertrust_cm_key` (and analogously `cm_group`, `cm_ssh_key`), refresh every updatable parameter derived from each resource's `Update()` source, eliminating attribute-drift blindness.
- Add `*_outOfBandDelete`, `*_outOfBandDrift`, and `*_writeOnlyFieldsPreserved` acceptance tests per resource, each with a mandatory `PlanOnly` follow-up step.
- Add the standardized TFIN-293 inline comment to every implemented Read.

### Preventive Actions
- Coordinate with TFIN-174 to document, in `CONTRIBUTING.md` or a provider design doc, the explicit policy: which resources must have real Read, which are intentionally empty, and how to mark exceptions (TFIN-293 comment style).
- Add a CI/review checklist: any new resource with non-empty Read must include an out-of-band-delete acceptance test plus a `PlanOnly` follow-up step; any resource with empty Read must cite the policy ticket inline.
- Audit remaining CM resources alongside TFIN-166 to confirm consistent 404 + drift handling.
- Consider extracting a shared `readResourceWith404Removal` higher-order helper once TFIN-166 and TFIN-293 land, to standardize the pattern across all subsystems.
