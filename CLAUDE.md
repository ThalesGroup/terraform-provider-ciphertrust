## What this repo is

The **CipherTrust Terraform Provider** lets users manage Thales CipherTrust Manager (CM)
resources using Infrastructure-as-Code. It translates `terraform plan/apply/destroy` calls
into CipherTrust Manager REST API calls. It is published at
`github.com/ThalesGroup/terraform-provider-ciphertrust` on branch `1.0.1`.

CipherTrust Manager (CM) is Thales's enterprise key-management platform. Provider
sub-areas: **CM** (core platform), **CCKM** (cloud key-management — AWS/Azure/GCP/OCI),
**CTE** (CipherTrust Transparent Encryption — file/volume encryption policies).

## ⚠ Critical project constraint — TFIN-174

**Empty `Read()` is the root cause of ALL drift issues.** Every resource's `Read` method
currently returns without calling the CM API, so Terraform never reconciles state against
reality. This masks all other bugs (immutable-field violations, case mismatches, tag swaps).

**Fix order is mandatory:**
1. Fix `Read()` first (TFIN-174) — once API is called during plan, all drift becomes visible.
2. Fix `RequiresReplace` on immutable fields (TFIN-183, TFIN-179, TFIN-181).
3. Fix case normalization and JSON tag issues (TFIN-195, TFIN-194).

If your task is NOT TFIN-174, do not implement a proper `Read()` as a side-effect — it will
surface drift before the immutable-field fixes are in and will confuse users. Leave `Read()`
empty unless the ticket specifically asks you to fix it.

# Implementation Plan: TFIN-290 — Drift Detection for `ciphertrust_cm_user`

## Context & Constraint

This ticket explicitly asks for drift detection on the `ciphertrust_cm_user` resource. Drift detection requires a working `Read()` method that fetches current state from CipherTrust Manager and updates the Terraform state accordingly.

**Per TFIN-174**, all resources currently have intentionally empty `Read()` methods. This ticket is one of the explicit exceptions — we are implementing `Read()` for `cm_user` only. We must take care that the implementation handles missing/deleted users gracefully (remove from state) to avoid the confusing drift errors TFIN-174 warns about.

## Files to MODIFY

### 1. `internal/provider/cm/resource_cm_user.go` (primary change)

**Pattern to follow:** Use `internal/provider/cckm/oci/resource_oci_vault.go` as the reference for a properly implemented `Read()` method against the Plugin Framework. Also cross-reference `internal/provider/connections/resource_azure_connection.go` for connection-style state mapping idioms.

Changes required in this file:

- **`Read()` method**: Replace the empty stub with a real implementation that:
  - Reads prior state into the resource's model struct via `req.State.Get(...)`.
  - Extracts the user ID (`user_id` / `id`) from prior state.
  - Calls the CM users API client (the same client used by `Create()` / `Update()` in this file) to GET the user by ID.
  - If the API returns a 404 / not-found error, call `resp.State.RemoveResource(ctx)` and return without an error so Terraform plans a re-create.
  - On other errors, append a diagnostic via `resp.Diagnostics.AddError(...)` and return.
  - On success, map every API response field back into the model struct, then `resp.State.Set(ctx, &model)`.

- **Field mapping**: Ensure every schema attribute that exists in `Schema()` is repopulated from the API response. Attributes that the CM API never returns (e.g. `password`, possibly `connection`) must be preserved from prior state — do **not** overwrite them with zero values, or Terraform will show spurious drift on every plan. Mirror how `resource_oci_vault.go` preserves write-only fields.

- **Sensitive / write-only handling**: `password` must remain untouched in `Read()`. Confirm its schema marks it `Sensitive: true` and that it is not refreshed from the API.

- **Computed-only fields**: Fields like `created_at`, `updated_at`, `last_login`, `account_lockout_at`, `failed_logins_count`, `user_id` should be refreshed from the API response.

- **Optional fields that may be nil**: For pointer / nullable response fields (e.g. `email`, `name`, `app_metadata`, `user_metadata`, `login_flags`), convert to the framework's `types.StringNull()` / object-null equivalents rather than empty strings, so plan diffs are stable.

## Files to CREATE

None. This is an in-place change to a single resource file.

## Schema Changes

None. No new attributes are introduced. Existing attributes' `Required` / `Optional` / `Computed` markers should be audited but not changed unless an attribute the API returns is currently missing `Computed: true` — in that case add `Computed: true` so refresh can populate it without diff churn.

## Breaking Constraints

- **TFIN-174 interaction**: This resource will diverge in behavior from all other resources in the provider after this change. Add a short comment block above the new `Read()` method in `resource_cm_user.go` explicitly stating: "Implemented per TFIN-290; other resources remain empty per TFIN-174."
- **No `RequiresReplace` changes**: This ticket does not introduce immutable fields, so existing replace semantics in the schema should not be modified.
- **Password drift**: Under no circumstances refresh `password` from the API. Doing so would either null it out or expose hashed values, both of which produce permanent diffs.

- Manual: Delete the user out-of-band, then `terraform plan` — resource must be planned for re-creation, not error out.
