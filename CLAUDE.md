## What this repo is

The **CipherTrust Terraform Provider** lets users manage Thales CipherTrust Manager (CM)
resources using Infrastructure-as-Code. It translates `terraform plan/apply/destroy` calls
into CipherTrust Manager REST API calls. It is published at
`github.com/ThalesGroup/terraform-provider-ciphertrust` on branch `1.0.1`.

CipherTrust Manager (CM) is Thales's enterprise key-management platform. Provider
sub-areas: **CM** (core platform), **CCKM** (cloud key-management — AWS/Azure/GCP/OCI),
**CTE** (CipherTrust Transparent Encryption — file/volume encryption policies).

## ⚠ Critical project constraint — TFIN-174

**Empty `Read()` is the root cause of ALL drift issues.** Every resource's `Read` method
currently returns without calling the CM API, so Terraform never reconciles state against
reality. This masks all other bugs (immutable-field violations, case mismatches, tag swaps).

**Fix order is mandatory:**
1. Fix `Read()` first (TFIN-174) — once API is called during plan, all drift becomes visible.
2. Fix `RequiresReplace` on immutable fields (TFIN-183, TFIN-179, TFIN-181).
3. Fix case normalization and JSON tag issues (TFIN-195, TFIN-194).

If your task is NOT TFIN-174, do not implement a proper `Read()` as a side-effect — it will
surface drift before the immutable-field fixes are in and will confuse users. Leave `Read()`
empty unless the ticket specifically asks you to fix it.

# Implementation Plan: TFIN-286

## Root cause

In `internal/provider/cm/schema_cm.go`, the `CMKeyJSON` struct (payload struct marshaled to the CipherTrust Manager REST API for key Create/Update requests) has its JSON tags swapped on two fields:

- `RevocationReason` is currently tagged `json:"revocationMessage,omitempty"`
- `RevocationMessage` is currently tagged `json:"revocationReason,omitempty"`

The Terraform schema attributes (`revocation_reason`, `revocation_message`, both `Optional`, `types.StringType`) and Go field names are correct; only the wire tags are wrong. CM therefore persists the values swapped. Per TFIN-174 every `Read()` is currently empty, so drift is not surfaced — but the data stored on CM is wrong.

## Files to MODIFY

### 1. `internal/provider/cm/schema_cm.go` (primary fix)

In the `CMKeyJSON` struct, replace the two buggy tags verbatim:

- Field `RevocationReason string` — change tag from `json:"revocationMessage,omitempty"` to `json:"revocationReason,omitempty"`.
- Field `RevocationMessage string` — change tag from `json:"revocationReason,omitempty"` to `json:"revocationMessage,omitempty"`.

Go field names are NOT renamed. The `omitempty` option is preserved exactly; only the field-name portion of each tag is swapped.

Pattern reference for correct CM REST camelCase tagging: the `AWSKeyJSON` struct in `internal/provider/cckm/aws/schema_aws.go` (fields such as `KeyState`, `KeyUsage`, `Description`) demonstrates the verbatim camelCase convention used across CM payload structs.

### 2. `internal/provider/cm/resource_cm_key.go` (verification — no change)

Definitive inspection result: `Create()` and `Update()` assign `CMKeyJSON.RevocationReason = plan.RevocationReason.ValueString()` and `CMKeyJSON.RevocationMessage = plan.RevocationMessage.ValueString()`. Assignments are field-name-aligned and correct. **No code change in this file.** The bug is exclusively in the JSON tags.

Per TFIN-174, `Read()` remains intentionally empty. Do not modify it.

### 3. `CHANGELOG.md`

Add a `Fixed` bullet under the next unreleased version:
`ciphertrust_cm_key: revocation_reason and revocation_message were transmitted with swapped JSON field names and stored swapped on CipherTrust Manager. Existing keys will be corrected on the next apply that touches these attributes (TFIN-286).`

## Files to CREATE

## Test plan

### Unit test (new)

File: `internal/provider/cm/schema_cm_test.go`
Function: `TestCMKeyJSON_RevocationTagsMarshaling`

Construct a `CMKeyJSON` value with `RevocationReason = "REASON_SENTINEL"` and `RevocationMessage = "MESSAGE_SENTINEL"`, marshal via `encoding/json`, and assert the produced JSON contains the substring `"revocationReason":"REASON_SENTINEL"` and `"revocationMessage":"MESSAGE_SENTINEL"`. A second sub-test asserts that omitting both fields produces neither key (verifies `omitempty` preserved).

### Acceptance test (new)

File: `internal/provider/cm/resource_cm_key_test.go` (existing file — MODIFY)
Function: `TestAccResourceCMKey_RevocationFields`

Add a new acceptance test step that creates a `ciphertrust_cm_key` with `revocation_reason = "Unspecified"` and `revocation_message = "decommissioned-by-acceptance-test"`, then issues a direct CM API GET via the test harness's HTTP client (pattern used by `TestAccResourceCMKey_basic` in the same file for out-of-band verification) and asserts the returned JSON body has `revocationReason == "Unspecified"` and `revocationMessage == "decommissioned-by-acceptance-test"`. This is required because `Read()` is empty (TFIN-174) and therefore cannot be used to detect the bug via state comparison; an out-of-band CM API assertion is the only automated way to catch a regression of the tag swap.

### Manual verification

Create a key with both attributes set, inspect the outgoing request in the CM audit log, confirm correct field placement.
